## 2. Постановка задачи

Предметная область проекта — прикладной погодный анализ для регионального уровня. Потенциальные пользователи: аналитики, муниципальные службы, агропредприятия, учебные демонстрации прогнозных моделей. Практический сценарий: быстро получить ориентировочные погодные параметры для выбранной территории и даты, а также показать прогноз на карте.

С точки зрения ML задача формулируется как supervised learning regression. На вход модель получает:

- координаты точки: `lat`, `lon`;
- календарные признаки: `month`, `day`, `dayofyear`;
- географические признаки: `sea_border`, `mountain_border`;
- административный центр: `admin_center`.

На выходе модель одновременно предсказывает 8 целевых переменных:

- `precipitation`;
- `temp`;
- `tmax`;
- `tmin`;
- `solar_radiation`;
- `wind_speed`;
- `wind_direction`;
- `day_length_hours`.

Основные метрики: MAE, RMSE и R² по каждому таргету. MAE и RMSE показывают абсолютную ошибку прогноза, а R² помогает понять, насколько модель лучше простого среднего прогноза.

## 3. Данные и EDA

В проекте используются табличные погодные данные по точкам Краснодарского края за 1995-2025 годы, данные о длине светового дня, инфраструктурные/географические признаки и GeoJSON муниципалитетов. Полные файлы находятся локально в `project/data/`, а небольшой пример структуры сохранён в `data/sample_data.csv`.

Основные файлы:

- `data/data.csv` — итоговая таблица для обучения и инференса;
- `data/Extended_climate_data.csv` — расширенные климатические данные;
- `data/Krasnodar_day_length_1995_2025.csv` — длина светового дня;
- `data/Krasnodar_infrastructure_1995_2025.csv` — дополнительные признаки территорий;
- `data/Krasnodar_Municipalities_GeoJson.txt` — границы муниципалитетов;
- `data/preprocess_data.ipynb` — подготовка и первичный анализ данных.

В ходе подготовки данные были объединены по дате, координатам и административным признакам. Были сформированы календарные признаки, проверены пропуски, распределения и географическое покрытие. Для демонстрации карты используется привязка точек к муниципальным полигонам.

Важное ограничение данных: осадки и направление ветра имеют высокую локальную изменчивость, поэтому хуже восстанавливаются по текущему набору признаков.

## 4. Модели и эксперименты

В качестве основной модели выбран ансамблевый подход `ExtraTreesRegressor`. Он хорошо подходит для табличных данных, устойчив к нелинейным зависимостям и не требует сложной нормализации признаков. Для подготовки признаков используется `Pipeline` с препроцессингом числовых и категориальных колонок.

Эксперименты находятся в `notebooks/train_model.ipynb`. В ноутбуке реализованы:

- разбиение данных по годам;
- обучение разведочной модели;
- расчёт MAE, RMSE и R² по каждому таргету;
- анализ важности признаков;
- подбор гиперпараметров через `RandomizedSearchCV`;
- обучение финальной модели и сохранение `model.pkl`.

Разбиение данных:

| Выборка | Годы | Количество строк |
|---|---:|---:|
| TRAIN | 2018-2023 | 1 794 260 |
| VAL | 2024 | 299 716 |
| TEST | 2025 | 293 313 |

Для поиска гиперпараметров использовалась 10% подвыборка TRAIN: 179 426 строк. Лучшие параметры:

| Параметр | Значение |
|---|---:|
| `model__max_depth` | 20 |
| `model__min_samples_split` | 5 |
| `model__min_samples_leaf` | 2 |
| `n_estimators` финальной модели | 50 |

## 5. Результаты

Сравнение разведочной и финальной модели:

| Выборка | MAE среднее | RMSE среднее | R² среднее |
|---|---:|---:|---:|
| VAL после TRAIN | 270139.9817 | 371349.9774 | 0.3320 |
| TEST финальная модель | 258330.7425 | 342409.7453 | 0.4659 |

Итоговые метрики финальной модели на TEST:

| Target | MAE | RMSE | R² | Оценка |
|---|---:|---:|---:|---|
| `precipitation` | 2.6839 | 4.1763 | -0.2387 | слабый таргет |
| `temp` | 3.2410 | 4.2010 | 0.8003 | хороший таргет |
| `tmax` | 4.0143 | 5.1757 | 0.7347 | хороший таргет |
| `tmin` | 3.2681 | 4.3749 | 0.7591 | хороший таргет |
| `solar_radiation` | 2066543.0 | 2739155.0 | 0.7139 | хороший таргет |
| `wind_speed` | 1.3029 | 1.6793 | 0.1059 | средний таргет |
| `wind_direction` | 88.1756 | 103.7608 | -0.1474 | слабый таргет |
| `day_length_hours` | 0.0275 | 0.0349 | 0.9998 | хороший таргет |

Финальная модель выбрана потому, что она улучшила средние MAE/RMSE относительно валидационной оценки и дала хорошие результаты для 5 из 8 целевых переменных. При этом ограничения по осадкам и направлению ветра явно зафиксированы и не скрываются.

## 6. Архитектура решения и сервис

Архитектура проекта:

1. `data/preprocess_data.ipynb` готовит итоговую таблицу.
2. `notebooks/train_model.ipynb` обучает модель и сохраняет артефакт.
3. `src/models/predictor.py` загружает модель, формирует признаки и выполняет инференс.
4. `src/service/main.py` предоставляет API.
5. `src/streamlit_app.py` предоставляет дополнительную визуализацию на карте.

API endpoints:

| Endpoint | Метод | Назначение |
|---|---|---|
| `/health` | GET | Проверка статуса сервиса и путей к данным/модели |
| `/regions` | GET | Список доступных административных центров |
| `/predict` | POST | Прогноз погоды по району/дате или конкретной точке |
| `/metrics` | GET | Базовые счётчики запросов и ошибок |

Пример запроса:

```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"admin_center":"Краснодар","date":"2026-06-15"}'
```

Пример ответа:

```json
{
  "admin_center": "Краснодар",
  "date": "2026-06-15",
  "points_used": 42,
  "predictions": {
    "precipitation": 2.1,
    "temp": 24.8,
    "tmax": 29.3,
    "tmin": 19.5,
    "solar_radiation": 7200000.0,
    "wind_speed": 3.4,
    "wind_direction": 186.2,
    "day_length_hours": 15.4
  }
}
```

## 7. Наблюдаемость, конфигурация и безопасность

В сервис добавлены:

- консольные логи запросов: метод, путь, статус, время ответа;
- endpoint `/health`;
- endpoint `/metrics` с базовыми счётчиками;
- обработка ошибок 404 для неизвестного `admin_center`;
- обработка 500 для ошибок инференса.

Конфигурация вынесена в `src/config.py`, `configs/config.yaml` и `configs/.env.example`. Реальные `.env`-файлы игнорируются через `.gitignore`. В проекте нет токенов, паролей или персональных данных.

## 8. Ограничения и дальнейшая работа

Ограничения текущей версии:

- крупные локальные файлы данных и модели неудобны для Git;
- модель хуже предсказывает осадки и направление ветра;
- нет MLflow или другого полноценного трекинга экспериментов;
- нет production-хранилища артефактов;
- Streamlit и API пока используют один локальный артефакт модели.

Что можно улучшить:

- сохранить облегчённую модель или вынести артефакт во внешнее хранилище;
- обучить отдельные модели для разных групп таргетов;
- добавить больше метеорологических признаков для ветра и осадков;
- подключить MLflow для версионирования экспериментов;
- добавить интеграционные тесты `/predict` с маленьким тестовым артефактом модели.
