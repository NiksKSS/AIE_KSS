# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- **Датасет:** `S12-hw-dataset.csv`. Прогнозировалась колонка `target` — числовой временной ряд.
- **Разбиение:** хронологическое — 70% train / 15% validation / 15% test.
- **Подходы:** B1 (naive-last), B2 (moving-average, окно 7), B3 (Ridge на лаговых и rolling-признаках), R1 (GRU, window_size=30).
- **Лучший подход:** выбирается по `val MAE` после сравнения всех четырёх экспериментов. Финальная оценка — один раз на test.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- **Как выполнен split:** данные сортируются по `date`, затем делятся хронологически:
  - **Train:** первые 70% наблюдений
  - **Validation:** следующие 15%
  - **Test:** последние 15%
- **Интервалы:** см. вывод ячейки 3 ноутбука, а также `artifacts/figures/series_split.png`
- **Почему random split некорректен:** при случайном разбиении будущие значения ряда попадают в обучающую выборку (data leakage). Модель фактически «видит ответы» — лаговые и rolling признаки, вычисленные для будущих точек, содержат информацию из прошлого, которое уже известно. В реальной задаче прогноза мы всегда предсказываем вперёд, поэтому граница train/test должна быть строго временно́й.

### 4.2. Признаки для baseline-моделей

- **Лаги:** `lag_1`, `lag_7`, `lag_14`
- **Rolling-признаки:** `rolling_mean_7`, `rolling_std_7`, `rolling_mean_14`
- **Календарные признаки:** `dayofweek`, `month`, `dayofmonth`, `weekofyear`
- **Обработка пропусков после лагов:** строки с NaN (первые 14 наблюдений из-за `lag_14`) удаляются перед обучением
- **Масштабирование:** `StandardScaler` — `fit` только на `train`, `transform` применяется к `val` и `test` отдельно

## 5. Модели и эксперименты (B1, B2, B3, R1)

- **B1 (`naive-last`):** прогноз = `lag_1` (последнее наблюдённое значение). Самый простой baseline, не требует обучения.
- **B2 (`moving-average`):** прогноз = `rolling_mean_7` (скользящее среднее за 7 последних наблюдений, сдвинуто на 1 шаг вперёд).
- **B3 (`ridge-lag-features`):** `Ridge(alpha=1.0)` на 10 признаках: lag_1, lag_7, lag_14, rolling_mean_7, rolling_std_7, rolling_mean_14, dayofweek, month, dayofmonth, weekofyear.
- **R1 (`gru-forecast`):** GRU (hidden=64, layers=2, dropout=0.2), оконное представление длиной 30 шагов, прогноз следующего значения.

**Дополнительные параметры:**

| Параметр | Значение |
|---|---|
| Основная метрика выбора | val MAE |
| Дополнительные метрики | RMSE, MAPE, sMAPE |
| window_size (GRU) | 30 |
| Batch size | 32 |
| Макс. эпох | 100 |
| Early stopping patience | 15 |
| Optimizer | Adam |
| Learning rate | 0.001 |
| Сохранение лучшей модели | по минимуму val_loss (MSE), `torch.save(state_dict)` |

## 7. Анализ

*(8–15 предложений — заполнить после просмотра результатов)*

Наивный baseline (B1) является важной точкой отсчёта: если ряд близок к случайному блужданию, его бывает трудно превзойти. Moving Average (B2) сглаживает шум, но запаздывает при резких изменениях ряда. Ridge на лаговых признаках (B3) учитывает несколько горизонтов сразу и добавляет календарную информацию, что позволяет явно моделировать недельную сезонность через `dayofweek`.

GRU (R1) работает на сырых последовательностях и способна обнаруживать нелинейные зависимости, недоступные Ridge. Её качество существенно зависит от объёма обучающих данных и гиперпараметров. При наличии выраженной сезонности или тренда GRU может значительно превзойти baseline; на шумных рядах без явной структуры выигрыш менее гарантирован.

Возможные источники утечек данных: использование `rolling` без сдвига `shift(1)`, обучение `scaler` на всей выборке, случайное перемешивание перед split. В данной работе все эти точки закрыты намеренно.

Оценка по validation принципиальна: если бы мы выбирали модель по test, это означало бы неявную настройку на тестовую выборку, и финальная оценка перестала бы быть честной.

## 8. Итоговый вывод

*(3–7 предложений — заполнить после просмотра результатов)*

Для задач краткосрочного прогнозирования временного ряда хорошим базовым подходом является Ridge на лаговых и rolling-признаках: он прост, быстро обучается и легко интерпретируется. Простых baseline (naive-last, moving average) достаточно как точки отсчёта и для оценки «пола» качества. GRU имеет смысл подключать при большом объёме данных, явной нелинейности и когда разрыв с табличными методами оправдывает затраты на подбор гиперпараметров. Главный вывод по валидации: temporal split — обязательное условие честной оценки, а не опциональная практика.
